## 二、核心问题

### 问题 A：技能模板无统一标准

kf-skill-design-expert 定义了"六步方法论"，但实际技能创建时未强制遵守：
- **kf-go** 的 `trigger` 字段直接在 frontmatter 顶层，而非 `metadata` 内
- **kf-alignment** 的 `principle` 字段在 `metadata` 内，但格式与其他技能不同
- 描述格式不统一：`Use when` vs `Load when` vs `中文描述`
- 并非所有技能都有 `graph` 依赖声明

### 问题 B：约束机械化不完整

- kf-go 和 kf-alignment 完全无约束门禁
- 即使有 Gate 的技能（如 kf-prd-generator），机械化验证命令也**未通过 Hook 自动触发**
- 验证失败缺**阻断逻辑**（Harness Engineering 铁律 2 评分 ≤ 3）
- 门禁跳过不会被察觉

### 问题 C：共享前缀未利用 KV Cache 优化

- 当前 shared-prefix.md 只有通用场景描述
- 无模型路由、无工具使用约束、无缓存预热指令
- 各 skill 的系统 prompt 前缀不一致，DeepSeek KV Cache 命中率低

### 问题 D：记忆持久化覆盖不全

- kf-go 和 kf-alignment 完全无记忆持久化
- 即使有持久化的技能，回读机制不统一（有的读 3 条，有的没有）
- 无过期清理策略

## 三、优化方案

### 3.1 技能模板标准化（Skill Template Standard）

**Frontmatter 标准结构：**

```yaml
---
name: skill-name              # 必填，与目录名一致
description: >-                # 必填，Use when... / Load when... 格式
  Load when user asks to ... User intent description with triggers.
metadata:
  pattern: pattern-name(s)     # 从 Five Design Patterns 选择
  recommended_model: pro|flash
  interaction: single-turn|multi-turn
  integrated-skills:           # 可选，联动技能列表
    - other-skill
graph:                         # 可选，依赖关系声明
  dependencies:
    - target: other-skill
      type: workflow|semantic|dependency
---
```

**描述格式标准化：** 统一使用 `Load when user asks to...` 或 `Use when user asks to...` 祈使句式。

**标准 Skill 结构：**

```
1. Context Collection（启动时自动收集上下文）
2. [Steps/Phases]（步骤式执行逻辑，每步有 Gate）
3. Iron Rules（MUST/MUST NOT）
4. Harness 反馈闭环（每个 Step 的验证动作表）
5. 记忆持久化（Memory Persistence）
6. Reference Files（按需加载的参考文件表）
```

### 3.2 约束机械化升级

**每个 Skill 必须包含：**
- 每个 Phase/Step 对应一个 Gate
- 每个 Gate 有 `harness-gate-check.cjs` 机械化验证命令
- 验证失败必须阻断后续流程

**Gate 标准格式：**

```markdown
### Gate N — {名称}

**验证命令：** `node {IDE_ROOT}/helpers/harness-gate-check.cjs --required-files "xxx" --forbidden-patterns "TODO"`

**失败阻断：** 未通过 MUST NOT 进入下一阶段。连续失败 2 次 → 升级为用户决策。
```

### 3.3 共享前缀优化

```markdown
### SHARED PREFIX START
## Project
You work in an AI coding IDE, multi-agent MVP rapid-prototyping system.

## Core Constraints
- Output files go to working directory.
- Prefer lean-ctx MCP tools for context efficiency (ctx_read > Read, ctx_shell > Shell, ctx_search > Grep).
- Report back to main session on completion.
- MUST NOT skip verification gates (Harness Engineering Iron Rule 2).
- Third-party services MUST be mocked (Iron Rule 2).
- Memory MUST be persisted and loaded on startup (Iron Rule 4).

## Communication
Use clear, concise responses. Use Chinese for user-facing communication.
### SHARED PREFIX END
```

### 3.4 记忆持久化标准化

每个可执行型 Skill 必须包含：

```markdown
## Memory Persistence (Iron Rule 4)

**启动加载：** 读取 `memory/{skill}-log.md` 最近 3 条记录作为历史基线。

**完成写入：** 每次执行完成后写入结构化摘要：
- date, project, input_source, core_modules, outstanding_issues
```
